## What I understood
- Transactions processing systems are systems with large databases and hundres of concurrent users executing database transactions.
    - These require high availability & fast response time for hundreds of concurrent users.

### Transactions
- Mechanism for describing logical units of database processing that must be completed in its entirety to ensure correctness.
- It is an executing program that forms a logical unit of database processing.
- It includes one or more database access operations.
    - Insertions, deletions, updates, or retrieval.
- The transaction's database opertaions can be embedded within an application program or specified interactively via a high-level query langauge (such as SQL).
- A way of specifying the transaction boundaries is to specify explicitly the begin transaction and end transaction statements.
- There are 2 types of transactions:
    - **Read-only transactions:** Database operations do not update the database, but only retrieve data.
    - **Read-write transactions:** Database operations update the database.
- Transactions submitted by various users may execute concurrently and may access and update the same database items.
    - That is why concurrency control and recovery mechanisms are needed.

#### Commit Point of a Transaction
- The **commit point** of a transaction happens when all its operations that access the database have been executed successfully *and* the effect of all the trasnaction operatoins on the database have been recorded in the log.
- Its effect must be permanently recorded in the database.
- If a system failure occurs, we search back in the log for all transactions that have written a start_transaction record into the log, but have not written their commit record yet.
    - These transactions may have to be rolled back to undo their effect on the database during the recovery process.
- Transactions that have written their commit record in the log must also have recorded all their write opreations in the log.
    - So their effect on the database can be re-done from the log records.

#### Force-writing the Log Buffer
- The log buffer will only write back to the disk when it is completely filled.
    - To save the overhead of mutiple disk writes of the same log file buffer.
- At the time of a system crash, only the log entries that have been written back to disk are considered in the recovery process (if the contents of main memory are lost).
- Therefore, *before* a transaction reaches its commit point, any portion of the log that has not been written to the disk yet, must now be written to the disk.

#### Desirable Properties of Transactions
- Transactions should have the **ACID** properties (and should be enforced by the concurrency control and recovery methods):
    - **Atomicity:** A transaction is an atomic unit of processing; it should either be performed in its entirety or not performed at all.
        - We should execute a transaction to completion.
        - It is responsibility of the *trasnaction recovery subsystem* of a DBMS to ensure this.
        - If a transaction fails to complete (for some reason), the recovery technique must undo any effects of the trasnaction on the database.
        - Otherwise, write operations of a committed transaction must be evetually written to disk.
    - **Consistency preservation:** A transaction should be consistency preserving, if it is completely executed from beginning to end without interference from other transactions.
        - It should take the database from one consistent state to another.
        - This is the responsibility of the programmers who write the database programs (and the DBMS module that enforces integrity constraints).
        - A **database state** is a collection of all the stored data items (values) in the database at a given point in time.
        - A **consistent state** of the database satisfies the constraints specified in the schema (as well as any other constraints on the database that should hold).
        - The database program should be written in a way that guarantees that, if the database is in a consistent state before executing the transaction, it will be in a consistent state after the *complete* execution of the trasnaciton (assuming that no interference with other transactions occurs).
    - **Isolation:** A transaction should appear as though it is being executed in isolation from other transactions.
        - Even though many transactions are being executed concurrently.
        - The execution of a transaction should not be interfered with by any other transactions executing concurrently.
    - **Durability/permanency:** The changes applied to the database by a committed transaction must persist in the database.
        - These changes must not be lost to any failure.
        - Responsibility of the *recovery subsystem*.

#### Levels of Isolation of a Transaction
- **Level 0:** It does not overwrite the dirty reads of higher-level transactions.
- **Level 1:** No lost updates.
- **Level 2:** No lost updates and no dirty reads.
- **Level 3 (true isolation):** No lost updates, no dirty reads, and repeatable reads.
- **Snapshot isolation:** A transaction sees the data items that it reads based on the committed values of the items in the database snapshot (or database state) when the transaction starts.
    - This will ensure that the phantom record problem does not occur.
    - The database transaction (or in some cases the database statement) will only see the records that were committed in the database at the time the transactoin starts.
    - Any insterions, deletions, or updates that occur after the transaction starts will not be seen by the transaction.

### Stored procedures
- The term used in the SQL standard is **persistent stored modules**.
- Procedures to enforce rules.
    - This is a provision to attach behaviour to the relations in the form of persistent stored modules.
    - They become a part of the overall database definition, and are invoked when certain conditions are met.
- These are program modules that are stored by the DBMS at the database server.
- Stored procedures are useful in the following circumstances:
    - If a database program is needed by several applications, it can be stored at the server and invoked by any of the application programs.
        - This reduces duplication of effort and improves software modularity.
    - Executing a program at the server can reduce data transfer and communication cost between the client and server (in certain situations).
    - These procedures can enhance the modeling power provided by view by allowing more complex types of derived data to be made available to de database users via de stored procedures.
        - Also, they can be used to check for complex constraints beyond the specificaiton power of assertions and triggers.
- Many commercial DBMS allow stored procedures to be written in a general-purpose programming language.
    - Also, they can be made of simple SQL commands (such as retrievals and updates).
- Because the procedures are stored persistently by the DBMS, it should be possible to call them from the various SQL interfaces and programming techniques.

#### Functions vs Stored Procedures
- Functions are computed values and cannot perform permanent environmental changes.
    - No insert or update operations are allowed.
- Sean K Anderson states that functions follow the definition that they must return a value and cannot alter the data they receive as parameters.
    - Functions are not allowed to change anything, must have at least one parameter, and must return a value.
- Stored procedures do not have to have a parameter, can change database objects, and do not have to return a value.
