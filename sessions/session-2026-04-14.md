## What I understood
Any data structure that can be adatped to the characteristics of disk devices can be used as a primary file organization for record placement on disk.

### Cardinality
- To be able to talk about index and its design, we also need to talk about **cardinality**.
- The cardinality of an attribute refers to the number of distinct values that the attribute can take on.
    - **Low cardinality:** small number of distinct values.
    - **High cardinality:** high number of distinct values.

### B-Trees (and B+-Trees)
- Special cases of tree data structures.
- These are search trees.
    - We use them as a mechanism to search for records stored in a disk file.
    - Each key value in the tree is associated with a pointer to the record in the data file having that value.
    - Wen a new record is inserted in the file, we update the tree by inserting an entry in the tree containing the search field value of the new record (and a pointer to the new record).
- The objective of these trees is that they are balanced.
- B+-Trees are just B-Trees where data pointers are stored only at the leaf nodes of the tree.


### Hash indexes
- Allow to access the file by using hashing on a searching key.
    - Search key is other than the one used for the primary data file organization.
-   The index entries are of the type <Key, pointer>.
- Only euqality conditions on searches apply.

### Composite index
- These happen when the primary (or secondary) keys on which the files are accessed consist of a combination of attributes.
- This works if a certain combination of attributes is used frequently.
- In an ordered index, keys are ordered lexicographically.
    - We first order by one key.
    - And we break ties with the other keys.
- A composite search key on columns (k_1, k_2, ..., k_n) "matches" a query if:
    - The query is a conjunction of m > 0 equality clauses on the form:
        - k_1 = < val_1 > *AND* k_2 = < val_2 > *AND* ... *AND* k_m = < val_m >.
    - And at most 1 additional range clause of the form:
        - *AND* k_m+1 < op > < val >.
            - Where < op > is one of { <, > }.
    - This happens because we need to be able to check the next row, and if it doesn't match, we must be able to finish the search.
- Beware if the set of records that meet each condition (of the composite search key) is large, yet only a few records satisfy the combined condition.
- If the set of records that meet each condition (of the combination of attributes) individually are large, yet only a few records satisfy the combined condition.

### Partial index
- A partial index is an index over a subset of the rows of a relation.
- In ordinary indexes, there is exactly one entry in the index for every.
- In partial indexes, only some subset of the rows in the table have corresponding index entries.
    - A partial index might omit entries for which the column being indexed is NULL.
- Partial indexes can result in:
    -   Smaller database files
    - Imporvements in query and write performance.

### Full scan
- If the address of the block that contains the desired record is not known, the search programs must do linear search through the file blocks.
- The goal of a good file organization is to avoid this linear search/full scan of the file.
    - And locate the block that contains a desired record with a minimal number of I/O operations.
